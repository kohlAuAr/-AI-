# Campus club platform working agreement

- This is a runnable thesis project. The bounded campus backend is implemented; new frontend integrations and AI extensions remain unfinished.
- Keep two independently running Spring Boot applications and one Vue frontend.
- `campus-service` owns formal campus business data. `ai-service` owns knowledge chunks and conversations.
- Demo data is public synthetic material. Do not describe it as real school data.
- Session login/CSRF, student registration/profiles/interests, manager-owned club creation/maintenance and recruitment toggles, scoped recruitment/review/withdrawal/memberships, activity draft/edit/publish/cancellation, signup/check-in, scoped participants, budget/expense/void summaries, account favorites and persisted notifications are implemented in campus-service. Free-text interest recommendation is implemented with configurable Embedding; real model quality is not verified. Password recovery, school SSO, payment/multi-level approvals, full AI document authorization, ReAct, MCP and DAG remain planned.
- LOCAL knowledge chat uses keyword retrieval and excerpts, never LLM generation. Recommendation can independently use Spring AI Embedding via EMBEDDING_PROVIDER=ollama/openai. Keep these two modes distinct.
- Normal developer mode connects club queries, registration/login, account profile/interests, recruitment, memberships, published activities, draft/publish, signup/cancellation and notifications to campus-service. Assistant recommendation uses only the signed-in account's free-text interest and current recruiting clubs. Profile saving never calls AI. Unconfigured Embedding returns 503 for semantic recommendation, never tag/mock fallback. Favorites remain browser-local. SAMPLE activities remain in the database but are not exposed as published events.
- Pure prototype/public builds set VITE_BUSINESS_API=false, keep browser-local mock workflows, and must not call business APIs. Keep the saved prototype archive unchanged.
- Keep LAN prototype mode separate from local API integration: vite.prototype.config.ts has no business proxy; normal developer integration pages live under /system.
- Keep model keys in environment variables or ignored local configuration. Never copy PaiSmart's credentials or database.
- Do not edit or restart the original `C:/workspace/PaiSmart` project as part of this project.
- Prefer small features across controller, service, persistence and frontend rather than empty abstractions.
- Verify backend changes with `mvn -DskipTests=false test`; frontend changes with `npm run build`.
- Verify integration with `node scripts/smoke.mjs` after starting the three processes.
- Verify the first business flow with `node scripts/check-recruitment.mjs`; after a campus restart use `node scripts/check-recruitment.mjs restored` to check the same saved record. These use synthetic demo accounts and do not delete existing records.
- Verify the activity flow with `node scripts/check-activities.mjs`; after a campus restart use `node scripts/check-activities.mjs restored`. Flow mode retains a one-seat synthetic activity; it cancels/rejoins only that named test activity, never deletes existing data. Activities are open to all student accounts; places are free text, not a venue reservation system.
- Verify notifications with `node scripts/check-notifications.mjs`; after restarting use `node scripts/check-notifications.mjs restored`. Flow mode creates a named synthetic activity and retained notifications; read-all changes only the student2 demo account. Do not backfill notifications for old business records or add queues/push without a new requirement.
- Verify new campus backend APIs with `node scripts/check-campus-backend.mjs`; after restarting use `node scripts/check-campus-backend.mjs restored`. Flow creates a separate synthetic account/club/activities and retains all financial/audit records. Do not touch old recruitment/activity/notification smoke fixtures.
- `restart-campus.ps1 -BackupData` restarts only the tracked campus process and copies the closed default H2 database; AI/frontend remain unchanged. Stop the campus process before repackaging its JAR on Windows. The backup switch is not a MySQL backup.
- Registration and account profile editing now have frontend controls. Manager club maintenance, activity editing/cancellation/check-in, finance and server favorites still do not. Preserve the saved prototype archive. Verify accounts with node scripts/check-account-profile.mjs (retains a separate synthetic student; no existing profile writes); frontend regression tests cover failed writes and late-response account isolation.
- Check-in is a manager-controlled code, open no earlier than 30 minutes before start and manually closed. Places and available-time profiles are free text; no GPS, venue inventory or automatic scheduling. Expenses use decimal amounts and activity-scoped UUID requestId; corrections void retained records, never erase them.
- Authentication uses Spring Security Session, not JWT. Never trust frontend role switches or caller-supplied userId. Demo accounts exist only under the demo profile; do not expose this local development system publicly.
- PLATFORM_ADMIN manages only homepage banners through /api/platform/**; it does not inherit MANAGER authority or club memberships. User registration always creates STUDENT. Banner uploads accept re-encoded PNG/JPG up to 2MB, while AI knowledge uploads still cap at 128KB. Bundled demo SVG illustrations are trusted source assets, not user-uploadable SVG.
- Banner public list/images filter enabled state, display window, recruitment closure and activity cancellation/start on each request; no push invalidation of already-open pages. Test with node scripts/check-banners.mjs; restored verifies the same retained offline fixture after restart. Never reseed banners on every restart or overwrite existing records.
- Preserve upstream license and source attribution for adapted code.
- Recommendation vectors are derived AI data cached by text hash and embedding provider/model version; interest/club text changes never reuse old vectors. Only recruiting state is a machine-enforced eligibility rule so far; requirements and available time remain prose, not automatic eligibility/scheduling. Test local flow with node scripts/check-interest-recommendation.mjs; restored reads the same retained synthetic account after restart; offline verifies profile writes while only AI is stopped. Real model quality and mobile browser acceptance remain separate checks.
- Spring AI 1.0.9 model libraries (not starters) handle native Ollama / compatible chat and Embedding. No automatic model downloads or registered tools. AI_MODE=ollama enables native chat and vector-indexed knowledge uploads; AUTO Embedding follows chat mode, explicit provider remains independent. Native URLs use the root without /v1. Old documents/history stay intact and startup never reindexes; reupload creates the current-version index. check-ollama-rag.mjs flow/restored/offline uses public synthetic materials; smoke.mjs is still LOCAL-only. check-interest-recommendation.mjs requires unconfigured Embedding except offline; use check-ollama-recommendation.mjs for native flow/restored/offline. restart-ai.ps1 manages only the verified tracked project AI process and reads ignored .env.local; never starts/stops the user's Ollama. Protocol fixtures and small real-model smoke cases are not a quality benchmark or production permission audit.
- Recommendation combines the full club name/category/description/tags text with BM25 (Chinese bigrams, lowercase English; k1=1.2, b=0.75) and semantic cosine via RRF(k=60). score is cosine, bm25Score is lexical, fusionScore is ranking, none is probability. BM25 is computed in memory without Elasticsearch and is not a silent fallback for model outages. Exclude only the exact check-campus-backend fixture naming+description convention from recommendation; retain all records and all other business APIs. Do not exclude all demo or manager-created clubs. Multi-interest smoke coverage is not a general coverage guarantee or negation understanding.
- User-approved Git workflow: after each requested new business feature or complete business slice is implemented and relevant checks pass, create a focused commit and push once to origin (https://github.com/kohlAuAr/-AI-.git). This is standing authorization for those completed feature pushes, not for unfinished work or unrelated changes.
- Inspect the worktree first, preserve unrelated user edits, stage only intended source/tests/docs, and exclude local configuration, credentials, databases, logs, dependencies and generated artifacts. Keep genuine commit dates and upstream attribution. Never force-push or overwrite remote changes; report conflicts or failed checks instead.
- After pushing, verify the remote branch matches the local commit and report the feature, actual checks and commit ID. If upload fails, report that the work is only local. For connection failures, inspect the currently configured proxy and use it per command when appropriate; do not change system proxy settings or disable HTTPS verification.
