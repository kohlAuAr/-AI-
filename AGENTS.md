# Campus club platform working agreement

- This is a runnable local thesis project. The bounded campus UI/backend and lightweight AI assistant are implemented; production school deployment remains out of scope. Current scope/evidence is in docs/PROJECT-ACCEPTANCE.md, docs/AI-ASSISTANT-WORKFLOW.md and docs/DELIVERY-GUIDE.md.
- Keep two independently running Spring Boot applications and one Vue frontend.
- Redis integration: see docs/REDIS-WORKFLOW.md. CAMPUS_REDIS_ENABLED enables 5-minute public club field caching (live member counts, after-commit invalidation with compare-and-set refill) and account-scoped atomic AI rate windows. Redis cache errors fall back to DB; failed rate checks reject new AI work with 503, leaving campus/history paths available. AI_REDIS_ENABLED separately controls 2-hour authorized recent-six-turn cache; context reads only last six DB turns and still rechecks permissions. Never cache admission decisions or replace DB signup constraints. scripts/redis-local.ps1 manages only isolated project Redis 16379; never stop existing 6379 or flush shared Redis. Opt-in real Redis tests: mvn -DskipTests=false '-Dredis.test.port=16379' test (isolated DB 14/15). check-redis.mjs flow/restored/offline retains its own fictional fixtures and uses invalid questions to avoid inference/fees. Daily billing quotas, model concurrency limits and Redis 7/production acceptance remain separate work.
- `campus-service` owns formal campus business data. `ai-service` owns knowledge chunks and conversations.
- Demo data is public synthetic material. Do not describe it as real school data.
- Session login/CSRF, student registration/profiles/interests, manager-owned club creation/maintenance and recruitment toggles, scoped recruitment/review/withdrawal/memberships, activity draft/edit/publish/cancellation, signup/check-in, scoped participants, budget/expense/void summaries, account favorites and persisted notifications are implemented in campus-service. AI has configurable hybrid interest recommendation, PUBLIC/CLUB document authorization, account-owned RAG/history, bounded read-only ReAct and activity planning with explicit human-confirmed draft saving. Small real-model cases are not a quality/security benchmark. Password recovery, school SSO, payments/multi-level approvals, arbitrary role administration, external MCP, DAG engines and multi-agent remain out of scope.
- LOCAL knowledge chat uses keyword retrieval and excerpts, never LLM generation. Recommendation can independently use Spring AI Embedding via EMBEDDING_PROVIDER=ollama/openai. Keep these two modes distinct.
- Normal developer mode connects club queries, registration/login, account profile/interests, club/recruitment settings, recruitment, memberships, activities/draft/edit/publish/cancel, signup/check-in, finance, account favorites and notifications to campus-service. Assistant recommendation uses only the signed-in account's free-text interest and current recruiting clubs. Profile saving never calls AI. Unconfigured Embedding returns 503 for semantic recommendation, never tag/mock fallback. Old local favorites are not auto-imported. SAMPLE activities remain in the database but are not exposed as published events.
- Pure prototype/public builds set VITE_BUSINESS_API=false, keep browser-local mock workflows, and must not call business APIs. Keep the saved prototype archive unchanged.
- Keep LAN prototype mode separate from local API integration: vite.prototype.config.ts has no business proxy; normal developer integration pages live under /system.
- Bootstrap model keys stay in environment variables or ignored local configuration. Admin-saved model keys are AES-256-GCM encrypted in the AI database using a separate AI_CONFIG_MASTER_KEY; never echo plaintext keys or ciphertext in API views/logs. Never copy PaiSmart's credentials or database.
- Do not edit or restart the original `C:/workspace/PaiSmart` project as part of this project.
- Current UI direction (2026-10-18) supersedes the older green community shell: adapt PaiSmart's Vue3/Naive UI layout, theme, login and conversation components under frontend/src/paismart while retaining campus APIs, Session/CSRF, role/account/club fences and all existing business controls. Mobile retains five bottom tabs plus a navigation drawer. Do not copy upstream credentials, JWT/billing/organization dependencies or unsupported controls. Preserve upstream attribution and the saved prototype archive. See docs/PAISMART-FRONTEND-ADAPTATION.md. SSR tests must use frontend/scripts/render.mjs to install the real css-render SSR adapter; do not replace real Naive UI components with test stubs.
- Prefer small features across controller, service, persistence and frontend rather than empty abstractions.
- Verify backend changes with `mvn -DskipTests=false test`; frontend changes with `npm run build`.
- Verify integration with `node scripts/smoke.mjs` after starting the three processes.
- Verify the first business flow with `node scripts/check-recruitment.mjs`; after a campus restart use `node scripts/check-recruitment.mjs restored` to check the same saved record. These use synthetic demo accounts and do not delete existing records.
- Verify the activity flow with `node scripts/check-activities.mjs`; after a campus restart use `node scripts/check-activities.mjs restored`. Flow mode retains a one-seat synthetic activity; it cancels/rejoins only that named test activity, never deletes existing data. Activities are open to all student accounts; places are free text, not a venue reservation system.
- Verify notifications with `node scripts/check-notifications.mjs`; after restarting use `node scripts/check-notifications.mjs restored`. Flow mode creates a named synthetic activity and retained notifications; read-all changes only the student2 demo account. Do not backfill notifications for old business records or add queues/push without a new requirement.
- Verify new campus backend APIs with `node scripts/check-campus-backend.mjs`; after restarting use `node scripts/check-campus-backend.mjs restored`. Flow creates a separate synthetic account/club/activities and retains all financial/audit records. Do not touch old recruitment/activity/notification smoke fixtures.
- `restart-campus.ps1 -BackupData` restarts only the tracked campus process and copies the closed default H2 database; AI/frontend remain unchanged. Stop the campus process before repackaging its JAR on Windows. The backup switch is not a MySQL backup.
- Registration, account profile editing, manager finance, activity editing/cancellation and account favorites have frontend controls. Preserve the saved prototype archive. Verify accounts with node scripts/check-account-profile.mjs (retains a separate synthetic student; no existing profile writes); frontend regression tests cover failed writes and late-response account isolation.
- Manager finance lives at /manage/finance and uses existing budget/expense/void/club-summary APIs; no payments or approval flow. Frontend only formats server-calculated money, shows null budgets explicitly, retains void reasons/times and reuses one UUID plus frozen expense content on retry. Scope changes synchronously clear financial records; late reads/writes cannot populate another account/club. Pure prototype finance stays browser-local and the saved prototype archive is untouched. Run npm run test:finance for Mock HTTP/SSR, npm run test:finance:live for a new retained synthetic draft, and npm run test:finance:live -- restored after a campus restart. These are not real browser/mobile acceptance.
- Club maintenance UI lives at /manage/club for owned managers only. Reuse GET /manage/clubs and PUT /manage/clubs/{id}, round-trip every field including campus; save is independent of AI. Recruitment closure is confirmed and retains existing applications/members; opening does not bypass duplicate/member rules. Scope changes clear forms and fence late responses; saved-write/failed-refresh and lost-response uncertainty are explicit. Successful writes clear stale local recommendation cards; recommendations derive fresh club text on the next request, not on settings save. Pure prototype has no settings route/API calls. Verify npm run test:club-settings and npm run test:club-settings:live; restored reads the same retained synthetic club after campus restart. No create-club UI, new approvals or schema change. See docs/CLUB-SETTINGS-WORKFLOW.md.
- Check-in UI is connected through CommunityCheckInPanel/checkIn.ts, student activity detail and personal registration records. Run npm run test:check-in and npm run test:check-in:live; after a campus-only restart run npm run test:check-in:live -- restored. These use Mock/real HTTP plus Vue SSR, not real browser/mobile acceptance. Scope changes synchronously clear codes/rosters and fence late responses; response-loss recovery reads authoritative state. Pure prototype stays unchanged.
- Check-in is a manager-controlled code, open no earlier than 30 minutes before start and manually closed. Places and available-time profiles are free text; no GPS, venue inventory or automatic scheduling. Expenses use decimal amounts and activity-scoped UUID requestId; corrections void retained records, never erase them.
- Authentication uses Spring Security Session, not JWT. Never trust frontend role switches or caller-supplied userId. Demo accounts exist only under the demo profile; do not expose this local development system publicly.
- Account security: POST /api/auth/password requires Session/CSRF and current password; PasswordService locks the account row, updates BCrypt plus credentialVersion, then the controller invalidates the current session after transaction commit. AccountPrincipal captures the login version; CredentialVersionFilter checks DB before CSRF and revokes stale sessions on their next request. Account uses DynamicUpdate so concurrent profile saves cannot restore an old password/version. AuthRateLimiter is bounded single-instance memory, not Redis: reserve at most five account login attempts in five minutes, clear on success; source login 120/min and registration 10/min; return 429/Retry-After. Counts reset on process restart; never trust browser-forwarded IP headers. See docs/ACCOUNT-SECURITY-WORKFLOW.md; test npm run test:account-security and scripts/check-account-security.mjs flow/restored with isolated fictional accounts. Do not change existing demo/student passwords for acceptance.
- PLATFORM_ADMIN manages homepage banners and platform model settings through /api/platform/**; it does not inherit MANAGER authority or club memberships. User registration always creates STUDENT. Banner uploads accept re-encoded PNG/JPG up to 2MB, while AI knowledge uploads still cap at 128KB. Bundled demo SVG illustrations are trusted source assets, not user-uploadable SVG.
- Model settings live at /platform/models. CHAT and EMBEDDING drafts are saved separately in ai-service; save never enables them. Revision-checked tests and explicit activation re-test precede atomic publication, with one pinned settings snapshot per synchronous student request. Durable active rows override bootstrap environment settings on restart; do not reseed/overwrite them. Exact deployment-owned AI_MODEL_ALLOWED_URLS restrict admin endpoints; OpenAI-compatible cloud requires HTTPS. No automatic cloud fallback, model downloads, server management or student billing. Embedding changes require acknowledgement; existing vectors remain and only matching versions are used, no automatic reindex. Single AI instance only; clustered configuration distribution, quotas and production deployment remain unimplemented. Verify mvn -DskipTests=false test, npm run test:model-settings, test:prototype and build; scripts/check-model-settings.mjs flow accepts only the same existing native localhost Ollama models, retains settings/audit and synthetic conversation, restored reads the same activation audit after AI restart, offline checks business queries with only project AI stopped. Never test paid cloud credentials without explicit user direction. See docs/PLATFORM-MODELS.md.
- Banner public list/images filter enabled state, display window, recruitment closure and activity cancellation/start on each request; no push invalidation of already-open pages. Test with node scripts/check-banners.mjs; restored verifies the same retained offline fixture after restart. Never reseed banners on every restart or overwrite existing records.
- Preserve upstream license and source attribution for adapted code.
- Initialize ignored local config using scripts/init-local.ps1; it generates AI_INTERNAL_TOKEN only if missing/blank and never prints it. Both backend processes need the same token, never a VITE variable. All /internal AI endpoints and /internal/ai/tools use service authentication. The campus gateway derives actor/membership from Session and the database, never from browser identity headers/JSON. Knowledge and conversation APIs require login, writes require CSRF. PLATFORM_ADMIN may upload PUBLIC documents but does not inherit access to CLUB documents. Managers may upload only for owned clubs. Old unowned conversations remain stored but unreadable; do not assign them to arbitrary users or relax ownership to pass old fixture tests.
- Shared conversation state clears synchronously on account/role changes and fences late responses. History rechecks document authorization; revoked references hide answer/observations. Redis keys include account and current club scope; cached context must equal authorized durable context. Fixed LOCAL queries are not model ReAct. Model ReAct has six read-only tools, at most three tool calls/four model rounds and bounded context. No enrollment/publish/payment/write/HTTP execution tools, external MCP or model thoughts in UI.
- Activity planning generates text only. The manager supplies real scheduling/capacity fields, reviews them and explicitly confirms PUT /manage/clubs/{clubId}/drafts/{requestId}; same UUID/body is idempotent, changed body conflicts. Frontend freezes the request on first attempt and reuses it after response loss. Pending confirmation state is memory-only; before refresh after an uncertain write, inspect the activity list. Publication remains a separate confirmed action. Verify npm run test:ai-workflows and node scripts/check-completion.mjs (OLLAMA only), restored after both service restarts, offline with only project AI stopped. These use isolated retained fictional data; browser/mobile acceptance must be stated separately.
- Recommendation vectors are derived AI data cached by text hash and embedding provider/model version; interest/club text changes never reuse old vectors. Only recruiting state is a machine-enforced eligibility rule so far; requirements and available time remain prose, not automatic eligibility/scheduling. Test local flow with node scripts/check-interest-recommendation.mjs; restored reads the same retained synthetic account after restart; offline verifies profile writes while only AI is stopped. Real model quality and mobile browser acceptance remain separate checks.
- Spring AI 1.0.9 model libraries (not starters) handle native Ollama / compatible chat and Embedding. No automatic model downloads or SDK-registered automatic tools; AgentService executes its own bounded read-only JSON allowlist. AI_MODE=ollama enables native chat and vector-indexed knowledge uploads; AUTO Embedding follows chat mode, explicit provider remains independent. Native URLs use the root without /v1. Old documents/history stay intact and startup never reindexes; reupload creates the current-version index. check-ollama-rag.mjs flow/restored/offline uses public synthetic materials; smoke.mjs is still LOCAL-only. check-interest-recommendation.mjs requires unconfigured Embedding except offline; use check-ollama-recommendation.mjs for native flow/restored/offline. restart-ai.ps1 manages only the verified tracked project AI process and reads ignored .env.local; never starts/stops the user's Ollama. Protocol fixtures and small real-model smoke cases are not a quality benchmark or production permission audit.
- Recommendation combines the full club name/category/description/tags text with BM25 (Chinese bigrams, lowercase English; k1=1.2, b=0.75) and semantic cosine via RRF(k=60). score is cosine, bm25Score is lexical, fusionScore is ranking, none is probability. BM25 is computed in memory without Elasticsearch and is not a silent fallback for model outages. Exclude only the exact check-campus-backend fixture naming+description convention from recommendation; retain all records and all other business APIs. Do not exclude all demo or manager-created clubs. Multi-interest smoke coverage is not a general coverage guarantee or negation understanding.
- User-approved Git workflow: after each requested new business feature or complete business slice is implemented and relevant checks pass, create a focused commit and push once to origin (https://github.com/kohlAuAr/-AI-.git). This is standing authorization for those completed feature pushes, not for unfinished work or unrelated changes.
- Inspect the worktree first, preserve unrelated user edits, stage only intended source/tests/docs, and exclude local configuration, credentials, databases, logs, dependencies and generated artifacts. Keep genuine commit dates and upstream attribution. Never force-push or overwrite remote changes; report conflicts or failed checks instead.
- After pushing, verify the remote branch matches the local commit and report the feature, actual checks and commit ID. If upload fails, report that the work is only local. For connection failures, inspect the currently configured proxy and use it per command when appropriate; do not change system proxy settings or disable HTTPS verification.
