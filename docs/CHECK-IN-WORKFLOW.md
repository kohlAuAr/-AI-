# 活动现场签到链

## 使用方法

负责人用 `photo_manager` 登录，进入 `/manage/activities`，在已发布活动下点击“签到与报名名单”。活动开始前 30 分钟起可点击“开启签到”；后端生成现场码，只向现场学生提供。页面显示有效报名人数、签到人数，以及每人的报名和签到时间。结束时点击“关闭签到”并确认。

学生用 `student` 登录，先报名该活动，再进入活动详情。负责人开启后点击“刷新签到状态”，粘贴现场签到码并确认。成功后详情显示签到时间，“我的 → 活动报名”同步显示“已签到”和时间。

演示密码 `CampusDemo123!`。所有资料均为本地虚构测试数据，开发服务不开放公网。

## 边界与规则

- 复用已有校园后端、Session/CSRF、所属社团权限和数据库；没有修改数据库结构或后端签到规则。
- 现场码是现有后端生成的 UUID，不是六位数字。未增加扫码、定位、场地预约、自动关闭或通知队列。
- 只有所属社团负责人可读取码、开启和关闭签到；平台管理员不自动拥有负责人权限。学生公开活动接口只暴露是否开启，不暴露码。
- 学生必须有有效报名。错误码、关闭状态、未报名和已取消报名均拒绝签到。输入前后空白会去掉，其他内容原样提交。
- 同一报名在开放状态下重复提交正确码返回原签到时间；关闭状态仍拒绝请求，不能以“曾签到”为由绕过校验。
- 已签到不能取消报名。关闭签到不删除记录；重新开启生成新码，旧码失效。
- 状态与人数由手动刷新读取，不宣称实时推送。开启的时间限制由后端判定，没有新增截止签到时间。
- 操作响应丢失时重新读取状态和个人记录，不自动反复写入。写入成功但读取失败会分别提示“已保存”和读取错误。
- 切换账号、角色、管理社团或活动时，清空旧名单、旧码和表单；迟到响应不能恢复旧上下文。页面隐藏不是权限保障，后端仍独立校验。
- 纯原型继续使用浏览器模拟活动，不调用签到业务接口，保存的原型归档未改。

## 请求与源码

学生输入码 → `activities.ts/checkInActivity` → 获取当前 CSRF → `POST /api/activities/{id}/check-in` → `ActivityService.checkIn` 校验 Session 学生、活动、开放状态、码和报名 → 首次保存 `checkedInAt` → 前端读取当前报名和活动。

负责人读取 `GET /api/manage/activities/{id}/check-in` 和 `GET /api/manage/activities/{id}/registrations`。开启/关闭为前者追加 `/open` 或 `/close` 的 POST；前端 `checkIn.ts` 将名单与签到状态一起加载，`CommunityCheckInPanel.vue` 负责展示和关闭确认。

学生入口在 `CommunityActivityDetail.vue`，个人记录在 `CommunityPersonalView.vue`；沿用现有白绿社群外壳、系统中文字体和列表层级。frontend-design 用于保持克制的内容组织，ui-ux-pro-max 用于输入标签、错误反馈、加载禁用、窄屏长码换行和账户上下文检查。

## 验收

- `npm run build`：类型检查与构建。
- `npm run test:check-in`：Mock HTTP + Vue SSR，覆盖角色范围、CSRF、提前开启、错误/关闭码、重复提交、响应丢失、读取/写入失败、记录显示和迟到响应隔离。
- `npm run test:business`、`npm run test:finance`、`npm run test:prototype`：回归现有业务、经费及纯原型。
- `mvn -DskipTests=false test`：两个后端测试；使用测试数据库，不是生产压测。
- `npm run test:check-in:live`：实际 Vue 客户端调用本地 HTTP，并进行 SSR 内容断言。新建一场明确标注的虚构活动，报名、签到、检查码轮换，最终关闭并保留记录。不会删除活动或改旧验收记录。
- 校园后端重启后 `npm run test:check-in:live -- restored`：核对 `.run/check-in-page-fixture.json` 的同一活动、报名 ID 和签到时间，不创建新签到。
