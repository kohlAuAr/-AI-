# 社团资料与招新设置链

## 入口与固定案例

负责人在工作台点击“社团资料与招新设置”，或从负责人导航进入 `/manage/club`。选择自己负责的社团后，可修改名称、类别、校区、兴趣标签、介绍、招新条件、日常活动时间/地点说明及招新开关，最后点击“保存资料与招新设置”。

例如摄影社补充“手机摄影、校园采风与新手教学”，招新条件写“欢迎零基础，不要求购买设备”。学生重新进入社团列表、详情时读取数据库中的新资料；详情显示校区和负责人填写的真实条件，不再写死“不限专业”。

本地演示账号 `photo_manager`、`code_manager`，密码 `CampusDemo123!`。学生账号 `student`、`student2`。资料均为公开虚构数据，不开放公网。

## 状态与权限

- 勾选“开放招新”只修改本页表单，保存成功才写数据库。页面始终标明“当前已保存状态”，不把未保存开关当成实际状态。
- 从开放改为关闭需要二次确认，确认会保存整份表单，而不只是开关。关闭只停止接收新入社申请；已有待审核申请、已加入成员、已发布活动及活动报名都保留。
- 关闭后仍能处理已有申请；重新开放恢复接收新申请，但不能绕过既有重复申请/已加入校验。
- 页面只读取后端返回的本人管理社团，保存目标为当前所属社团。学生、其他社团负责人、平台管理员不能据此获得修改权限；后端独立执行 Session、CSRF、所属关系和字段约束校验。
- 没有新增创建社团入口、学校审批、角色管理、自动资格审核、课表冲突判断或场地预约。

## 资料与 AI 的边界

社团资料属于 `campus-service` 的正式业务事实。保存和读取设置不调用 AI 服务；没有引入新的向量化队列或消息中间件。

下一次兴趣推荐请求仍由校园后端读取招新中的社团，以名称、类别、介绍、标签组成完整文本，交给既有 BM25 + Embedding + RRF 流程。向量派生缓存按文本和模型版本区分；设置页面不预先重建向量。校区、招新条件和时间说明不因此变成自动过滤规则。

保存成功会清空当前浏览器内已有的推荐卡片，避免旧说明继续被当成新结果；其他已打开客户端没有实时推送，需重新读取或重新请求推荐。本次没有运行新的真实模型质量评估，不能将资料保存成功称为推荐效果提升的证明。

## 实现及失败路径

- `CommunityClubSettings.vue`：沿用白绿社群外壳、系统中文字体和原生表单；窄屏单列，宽屏两列；错误摘要带字段链接并获取焦点，字段保留各自错误。两个字段分组由 frontend-design 组织，ui-ux-pro-max 用于标签、状态反馈、触控与错误恢复检查。
- `clubSettings.ts`：`GET /api/manage/clubs` 读取完整原始字段，避免从旧展示模型回填而漏掉校区；`PUT /api/manage/clubs/{id}` 保存，后端接口和表结构未改。
- 保存失败保留输入和原来的已保存值，提示重新读取核对；网络响应丢失不自动重写。保存成功但刷新失败明确分别报告，不误报未保存。
- 切换账号、角色或管理社团同步清空旧表单、确认弹窗及提示，迟到响应不能覆盖新上下文。选择其他社团会放弃当前未保存修改；“重新读取资料”在有修改时二次确认。没有自动保存或多编辑者乐观锁。
- `business.ts` / `data.ts` 将现有 API 校区传递给学生详情，`recommendations.ts` 在保存后清空旧推荐状态。导航及工作台新增设置入口。
- 纯原型不注册该正式设置路由、不展示设置入口，直接调用设置模块也不请求业务 API；保存的原型归档和原有浏览器模拟流程未改。
