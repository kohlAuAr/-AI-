# 校园业务后端：范围、使用与源码路线

## 本次交付到哪里

本轮补齐 campus-service 的校园业务 API，不扩展 ai-service，不重新设计前端。当前招新、发布/报名和消息页面继续可用；注册/资料、社团维护、活动编辑/取消/签到、经费及账号收藏的页面对接是后续工作。

“后端补齐”指下面约定的业务范围，不是支付、正式学校身份、任意角色管理等所有校园系统功能都已完成。地点和空闲时间直接存文字，不建设场地库或排课系统。

| 业务 | 学生可以做什么 | 所属负责人可以做什么 |
|---|---|---|
| 账号与资料 | 注册为学生、登录、修改本人姓名/专业/兴趣/空闲时间 | 登录并修改本人资料；本轮不提供账号提权 |
| 社团与招新 | 查看资料、申请/撤回、看本人审核结果和成员关系 | 创建自己负责的社团、维护资料/招新开关/条件、审核申请、看成员 |
| 活动 | 看已发布活动、报名/取消、看本人记录、凭有效码签到 | 草稿/编辑/发布/取消、查看名单、开启/关闭签到与统计 |
| 经费 | 不能读取负责人财务接口 | 设置活动预算、记支出、作废误录、查看活动/社团汇总 |
| 收藏与通知 | 本人账号收藏/取消收藏、本人通知及已读 | 本人账号收藏/通知；不能读取其他账号私有记录 |

## 一个完整例子

假设“摄影社”的负责人发布“构图交流”，学生小林参加：

1. 小林注册并登录，填写兴趣“摄影”、空闲时间“周三晚上”。这些是本人资料，暂不自动推荐或计算时间冲突。
2. 负责人维护摄影社的招新说明和开关。小林申请入社，负责人审核通过；申请状态和成员关系一起保存。
3. 负责人创建活动草稿，填开始时间、报名截止、地点和容量，再确认发布。小林报名，名额计数增加，收到本人站内通知。
4. 小林已报名后，负责人可以修正文案，但不能悄悄更改开始时间或地点；活动确需取消时填写原因，系统保留活动历史、取消有效报名并通知每个报名者。
5. 正常举办时，负责人最早在开始前 30 分钟开启签到，取得现场码。小林提交码，系统核对活动、开关、报名和码，保存签到时间；当前码有效时重复提交不会变成第二次签到。负责人结束后手动关闭。
6. 负责人设置预算 100.00 元、录入材料支出 18.50 元。客户端为这笔支出生成 UUID，网络重试复用它；不会重复记账。误录时填写作废原因，原始金额/日期和作废人/时间保留，不算入有效支出。
7. 小林收藏摄影社，数据绑定登录账号。换浏览器重新登录仍能查询同一收藏；当前前端收藏页尚未接此接口，仍是浏览器本地演示记录。

不自动报名、不自动发布、不自动审批。这些仍由确定身份的学生或负责人明确提交。

## 接口怎么使用

本地三进程运行后，统一调用 `http://127.0.0.1:5178/api`（前端开发代理）或校园服务 `http://127.0.0.1:8090/api`，不要在同一个会话里混用不同主机地址。所有写请求，包括匿名注册，都需要 CSRF：

1. GET `/api/auth/session`，保留 Cookie，读取 csrfHeader 和 csrfToken。
2. 写请求使用该 header/token，并带 Cookie。登录为表单 username/password；业务请求为 JSON。
3. 登录、退出后重新获取 CSRF。业务身份来自 Session，不通过 userId 或前端角色按钮指定。

完整 API、输入上限与请求例子见 [API.md](API.md)。演示负责人 `photo_manager` 和 `code_manager`、密码 `CampusDemo123!` 只用于本地虚构数据。新注册账号一律 STUDENT；本轮不提供负责人申请或角色分配接口。

运行自动验收可直接使用：

```powershell
cd C:\workspace\campus-club-platform
node scripts/check-campus-backend.mjs
powershell -ExecutionPolicy Bypass -File scripts/restart-campus.ps1 -BackupData
# 等待校园服务启动后，检查同一批数据，而不是新建一批冒充持久化。
node scripts/check-campus-backend.mjs restored
```

首次 flow 会新增一套明确标注的虚构账号、社团和活动；不删旧业务记录。仅联调注册账号采用公开演示密码，不用于真实账号。签到测试活动在脚本运行时开始后约 20 分钟，属于小规模开发验收，不是性能压测。

## 为什么这些规则放在后端

前端禁用按钮只能改善体验，不能防止用户直接发送请求。后端必须再核对：当前是谁、是不是本社团负责人、记录现在什么状态、是否超过名额或截止。

关键规则：

- 草稿单独确认才发布；SAMPLE 占位活动不当作已发布活动或记账对象。
- 已有人报名后不改时地；容量不能小于有效报名人数；活动开始后不能编辑或取消。
- 活动取消保留原因和操作人，不删除报名历史；已签到不允许再取消。
- 签到开启时间下限为开始前 30 分钟，没有自动结束时间，负责人必须关闭。码只给所属负责人；这是基础签到，不防止学生转发现场码，不声称定位或反作弊。
- 报名、编辑、取消、签到与财务写入锁定相同活动行，避免并发状态互相覆盖。收藏按社团行串行化，并有用户—社团唯一键兜底。
- 支出金额最多 8 位整数和 2 位小数，使用十进制计算；支出必须为正、发生日期不在未来。超预算提示而非禁止录入已经发生的真实费用。
- 未设置预算时 budget/remaining 为 null，不当作零预算；作废支出仍保留并返回，但不参与有效合计。
- 同一支出 requestId 不同内容返回 409；已作废记录的原请求重试返回原 VOID 记录，不复活它。
- 活动取消与通知同一事务。任何一步失败，都不能留下“活动取消了、学生报名还有效”之类半完成状态。

## 从哪里读代码

建议一次读一个具体请求，不从所有类开始背：

| 请求链 | 控制器 → 业务服务 → 持久层 |
|---|---|
| 学生注册/本人资料 | `identity/ProfileController` → `ProfileService` → `AccountRepository` / `Account` |
| 社团创建/招新维护 | `club/ClubManagementController` → `ClubManagementService` → `ClubRepository` / `MembershipRepository` |
| 账号收藏 | `favorite/FavoriteController` → `FavoriteService` → `FavoriteRepository` |
| 活动编辑/取消/签到 | `activity/ActivityController` → `ActivityService` → `ActivityRepository` / `RegistrationRepository` / `NotificationService` |
| 预算/支出/作废 | `finance/FinanceController` → `FinanceService` → `ExpenseRepository` / `ActivityRepository` |

文件均位于 `campus-service/src/main/java/com/campus/business/`。身份和 CSRF 看 `identity/SecurityConfig`、`IdentityService`；输入校验看各控制器的 request record；越权、状态与事务看 Service；最后读实体、Repository 唯一键和锁。

例如先读 `FinanceService.add()`：输入是某活动 ID 和一笔支出；先锁活动、核对负责人，再查 UUID。存在且内容相同就返回原记录；内容不同报冲突；不存在才保存。再看测试 `BusinessCompletionApiTest.concurrentExpenseRetryWritesOneEntry()`，理解“为什么两次请求只算一笔”。

## 暂不包含的内容

没有支付、发票上传、复杂审批、成员踢出/退出、密码找回、正式学校 SSO、任意角色管理、自动场地调度、定位签到、消息队列或实时推送。没有因此宣称已经完成 AI 推荐、ReAct、MCP、DAG 或完整 AI 资料权限。

默认 H2 文件库仅用于本地开发；MySQL 迁移和实测、生产限流/注册防滥用、分页及性能测量仍需另行实施。不得把这些本地演示接口直接发布到公网。

下一步建议接通新增前端入口，再从已稳定的校园只读接口接入兴趣推荐与 AI 助手。
